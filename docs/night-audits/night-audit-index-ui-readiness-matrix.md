# Night Audit Index UI Readiness Matrix

## Source Reference

| Source | How This Matrix Uses It |
|---|---|
| `night_audit_comparison_matrix.md` | Primary source of truth for current Night Audit readiness, MVP scope, implemented behavior, gaps, anomalies, and business-date governance. |
| Business-date rule | The UI must treat `HotelBusinessDate` as accounting authority. Calendar-derived dates are only scheduling/default calculations and must not decide the audit target. |
| Current UI risk | Existing labels and controls can make the page feel like a manual job runner. The redesign should position it as a Business Date Control Center. |

## Missing Backend Fields / Presenter Needs

| Need | Why It Matters | Current Signal From Comparison Matrix | UI Recommendation |
|---|---|---|---|
| Derived UI state | The view needs `READY_FOR_AUDIT`, retry, blocked, failed, and force-close presentation without mixing model statuses. | `READY_FOR_AUDIT` is derived; `failed` is a NightAudit status, not a HotelBusinessDate status. | Add a presenter/view model that exposes `ui_state`, `status_badge`, `primary_action`, and disabled reasons. |
| Explicit `closable_now` | Avoid confusing calendar date with closable business date. | Clock-derived dates are expected-date calculations, not posting authority. | Expose whether the current business date can close now and why. |
| Hotel-local calendar date | The page must explain why business date can lag calendar date. | Hotel timezone and business windows exist. | Expose calendar date in hotel timezone instead of relying on server date. |
| Run-level failure summary | Failure details are stored in logs/events but not directly on the run. | Comparison matrix marks failure error as partially implemented. | Surface normalized failure message through presenter/API before UI overhaul. |
| Run-specific vs snapshot counts | Users need to know what this run changed versus what currently exists. | `review_no_show_count` anomaly: current total can overstate moved-by-this-run count. | Label counts as `This run` or `Current snapshot`; avoid ambiguous totals. |
| Per-blocker resolution metadata | Staff need guided resolution. | Follow-up recommends deeper guided resolution actions. | Expose blocker category, affected record, action label, route, and severity. |
| Direct NightAudit charge linkage | Reconciliation needs reliable run-posted totals. | Metadata-only `night_audit_id` lacks relational integrity. | Until backend changes, label run-posted data based on available run_results/metadata and avoid overstating certainty. |
| Operational edit lock state | UI should warn or disable risky edits during audit. | Financial posting is guarded, but booking/status edits can race. | Expose audit lock state for relevant booking timeline/status actions. |
| Force-close evidence read model | Force-closed history needs durable evidence in one place. | `hotel_business_dates.force_close_reason`, `force_closed_at`, `force_closed_by_id`, `blockers_snapshot`, and financial audit events exist. | Presenter should gather actor, reason, event, and blocker snapshot into one read model. |

## Current UI Copy Replacement Matrix

| Current Term | Replacement Term | Reason |
|---|---|---|
| `Pre-Audit Check` | `Close Readiness` | Aligns the card with blocker/warning readiness rather than a one-off check. |
| `Manual Run` | `Audit Action` | Avoids making the page feel like a manual job runner. |
| `Force Roll` | `Force Close Business Date` | Makes the accounting risk and business-date effect explicit. |
| `Completed At` | `Finished At` | Blocked/failed attempts also end; `Completed` implies successful close. |
| `Ready for Audit` after failure | `Retry Available` or `Audit Can Be Retried` | Avoids implying a clean first-run state after a failed attempt. |
