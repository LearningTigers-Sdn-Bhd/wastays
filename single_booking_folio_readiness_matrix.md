## Current Architecture Summary

The current implementation has a real single-booking folio foundation. `BookingFolio` is a one-to-one child of `Booking`, and `FolioTransaction` is the posted financial ledger. Forecasted charges are separated into `FolioForecastedCharge`, then actualized by posted transactions.

Financial posting is mostly centralized through `Folios::InsertTransaction`, which locks the folio, enforces permissions, applies business-date posting guards, writes `FolioTransaction`, and records `FinancialAuditEvent`. Higher-level services wrap it for staff posting, reversals, nightly charges, gateway payments, refunds, catch-up charges, and checkout closing.

Manual booking creation and public confirmation now initialize a folio after rooms and payment records exist. Check-in, walk-in, backdated check-in, no-show finalization, and reinstatement retain idempotent initialization as a safety net. `Folios::BackfillMissingForOperationalBookings` and `folios:backfill_missing` provide an operational repair path for eligible legacy bookings outside Night Audit.

Night Audit posts nightly accommodation and tax through `Folios::PostNightlyCharges`, with `night_audit_id`, metadata, and unique nightly posting keys. Missing folios are now pre-close blockers, so `NightAudits::Run` stops before posting rather than silently completing after a defensive skip. Checkout flows through `Bookings::TransitionStatus#check_out`, which calls `Folios::CloseForCheckout` before moving the booking to `completed`.

Priority #1 financial safety hardening remains in place for catch-up idempotency, authoritative backdated posting dates, required DB fields, touched override-param paths, and checkout local payment/refund sync readiness. Priority #2 lifecycle hardening adds explicit open/closed status rules, creation-time initialization, pre-posting Night Audit protection, controlled reopen, legacy backfill, and broader lifecycle coverage. The remaining gaps are mostly cancellation policy, transaction-code configuration, uniform reason requirements, and selected rollback/financial-summary coverage.

## Missing Core Pieces

- First-class transaction code configuration if categories are not sufficient.
- Full cancellation folio policy.
- Consistent reason requirements for write-offs, manual adjustments, and refunds.
- A staff-facing reopen route/UI, only if operationally required; the controlled service already exists.
- Broader rollback tests for injected failures during reinstate/no-show lifecycle transitions.
- Stronger Night Audit financial summary coverage around reversals, refunds, write-offs, and retries.

## Dangerous Or Risky Current Behavior

- Some non-touched flows still expose or pass explicit override options, including check-in/reinstate paths; the touched reversal/checkout/backdated catch-up paths were cleaned up.
- Existing operational bookings created before Priority #2 may still lack folios until `folios:backfill_missing` is run; Night Audit now blocks these before posting.
- Public confirmation during `audit_running` may create the non-posting folio container, but captured-payment synchronization still obeys posting guards and can cause confirmation to fail rather than bypass financial controls.
- Cancellation changes booking/inventory state without clear folio close, refund, or charge policy.
- Security deposits are linked to folios but not included in `outstanding_balance`, which is probably correct for liability treatment but needs explicit policy.
- Checkout sync can persist local payment/refund folio transactions before checkout later fails on recalculated balance; this is intentional local sync behavior but should be operationally understood.
- Financial summary relies on `posting_date` totals and needs stronger tests around reversals, refunds, write-offs, and audit retry scenarios.

## Recommended Build Order

1. Run `folios:backfill_missing` outside `audit_running` and review any failed legacy bookings.
2. Define cancellation folio/refund policy separately without weakening the current lifecycle guarantees.
3. Harden transaction categories or add transaction codes if operational configuration is needed.
4. Standardize reason requirements for write-offs, refunds, and manual adjustments.
5. Continue replacing explicit override options in remaining non-touched lifecycle flows with server-derived context.
6. Keep forecasted charges separate from posted transactions and strengthen forecast actualization tests.
7. Preserve posted transaction immutability, reversal-only correction behavior, and service-only close/reopen paths.
8. Keep business date, currency, status constraints, and DB-backed idempotency keys enforced.
9. Keep Night Audit-posted transactions linked through `night_audit_id`; add stronger financial summary and retry rollback tests.
10. Continue centralizing posting through `Folios::InsertTransaction`; avoid controller/model direct writes.
11. Add explicit reinstate/no-show injected-failure rollback specs and true concurrency coverage where operational risk justifies it.
12. Add a staff-facing controlled reopen action only if operations require it; keep authorization in `Folios::ReopenForCorrection`.
