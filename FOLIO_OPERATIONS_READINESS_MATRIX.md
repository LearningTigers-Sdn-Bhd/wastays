# Folio Operations Readiness Matrix

Scope: readiness review for folio operation items #1-#5 before implementation. This review uses application code and specs only; the `docs/` folder was not used as source of truth.

Completed context already assumed: folio index page, transaction code management, and tax attachment to transaction codes.

Recommended balance rule: positive balance means guest owes hotel, zero means settled, negative balance means hotel owes guest.

## Suggested Execution Order

| Step | Task | Why It Comes First | Depends On |
|---|---|---|---|
| 1 | Verify folio show information architecture | Staff needs one reliable control center before adding more actions. Header, balance state, references, and ledger shape determine the rest of the UI. | Existing folio show route, booking presenter, booking folio associations |
| 2 | Verify manual insert transaction flow | Posting must obey transaction-code-derived category/sign/tax behavior before reversal or close rules can be trusted. | Transaction code management, tax attachments, `Folios::PostStaffTransaction`, posting guard |
| 3 | Verify transaction display and reversal behavior | Staff must understand immutable posted rows and safely correct mistakes before closing folios. | Completed ledger shape, manual posting rows, tax-line linkage |
| 4 | Verify folio close behavior | Close eligibility depends on accurate balances, posted charges, synced payments/refunds, and clear correction policy. | Ledger totals, payment/refund sync, missing forecast detection, reversal policy |
| 5 | Run night audit regression check | Night audit is the highest-risk automated posting path after transaction-code/tax changes and should be verified after manual rules are clear. | Transaction code defaults, tax snapshots, posting guard, close rules |

## Likely P0 Risks

| Risk | Why It Is P0 | Check/Fix |
|---|---|---|
| Folio show does not visibly distinguish booking reference from folio reference. | Staff may operate on the wrong financial document. | Add folio number/reference to compact header and keep booking confirmation separate. |
| Balance display does not explicitly say guest owes hotel, hotel owes guest, or settled. | Negative balances and zero balances can be misinterpreted during checkout/close/refund decisions. | Add shared balance-state helper/presenter rule matching close behavior. |
| Reversing a parent charge may not reverse attached tax rows atomically. | Balance and tax reports can remain wrong after correcting `ROOM_CHARGE`, `EXTRA_BED`, or other taxable charges. | Define and implement grouped reversal for transaction-code-generated tax rows, or explicitly require linked tax reversal in UI. |
| Ledger lacks transaction code, debit/credit split, running balance, reference, and action controls. | Staff cannot audit or safely reverse the right row from the folio control center. | Expand canonical ledger table before adding operational actions. |
| Night audit may not be fully proven against transaction-code tax attachment changes. | Manual posting can be correct while automated nightly postings, catch-up charges, or blockers regress. | Add/run targeted regression specs for ROOM default code, SST, Tourism Tax, catch-up idempotency, and audit financial summary totals. |
| Staff inserts during `audit_running` need request-level proof. | Posting during audit can invalidate financial close. | Add request spec for normal manual insert blocked during `audit_running`; preserve blocker-resolution exception only where intended. |

## Implementation Questions Before Coding

| Question | Decision Needed |
|---|---|
| Should folio show expose a standalone `Close Folio` action, or should closing remain only inside checkout flow? | Determines routes, RBAC, button visibility, and whether `CloseForCheckout` is reused directly or wrapped. |
| What is the required folio reference display: raw `folio_number`, formatted folio number, invoice number after close, or all of them? | Prevents ambiguous header labels and invoice/folio confusion. |
| Should manual posting support `quantity` and `reference` for MVP? | Determines schema/metadata, form fields, audit metadata, and ledger columns. |
| Should manual posting require a preview when attached taxes will post additional rows? | Determines whether to build a preview endpoint/calculator or just show configured tax attachments in the modal. |
| When reversing a taxable parent transaction, should the system reverse linked tax rows automatically? | Recommended: yes, atomically, for rows linked by `parent_folio_transaction_id` or source metadata. |
| Are closed-folio corrections allowed by policy, and if yes should staff reverse on closed folio or reopen through controlled workflow? | Determines action visibility and permission model for closed folios. |
| Which permission controls folio close from the folio page? | Needed before adding close button; current posting permissions do not clearly cover closing. |
| How should running balance treat forecasted charges? | Recommended: posted running balance only, with forecasted projected balance shown separately. |
| Should payment/refund rows display gateway/reference metadata separately from manual cash/refund entries? | Determines ledger reference/source columns and reconciliation visibility. |
| What exact default transaction code should night audit use for room revenue after hotel-specific code customization? | Confirm `room_revenue` system key remains authoritative while displaying hotel-customized code. |
